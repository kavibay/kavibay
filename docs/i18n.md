# Translating the host UI

Kavibay ships in English only. Host strings already go through a translation
layer, though, so another language is a catalog file rather than a refactor.
The layer lives in `core/app/i18n/`.

## Using it

```ts
import { t } from "../i18n/i18n";

t("settings.nav.about");                          // "About"
t("about.version", { version });                  // "Version 0.1.4"
t("extensions.bulkAdd.added", { count: added });  // "Added 1 widget." / "Added 4 widgets."
```

In a template, call `t()` in the template itself, e.g. `{{ t("about.title") }}`. It is
reactive: `t()` reads the active locale, so a template or `computed` that calls it
updates when the locale changes. A string resolved at module load does not update. When
data declares text (as the Settings nav does), store the **key** and call `t()` when
rendering. See `settingsNavGroups()` in `core/app/settings/settingsNav.ts`.

## Adding a string

1. Add the key to `core/app/i18n/messages/en.ts`. Keys are flat and dotted,
   `area.thing`, grouped by the surface that shows them.
2. Use `{name}` for a value. A plural message is an object of
   [`Intl.PluralRules`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/PluralRules)
   categories (`one`, `few`, `other`…). `other` is required, and plural messages require a `count`
   parameter.

Keys and parameters are typed from `en.ts`. An unknown key, a missing or misspelled
parameter, or parameters passed to a plain string all fail `pnpm run typecheck`.

Don't build sentences from pieces (`"Added " + n + " widget" + s`). Word order and
plural rules differ between languages. One message with placeholders lets a
translator move the parts around.

## Adding a language

1. Copy `messages/en.ts` to `messages/<lang>.ts` and translate the values. A key left
   out falls back to English.
2. Register it in `CATALOGS` in `core/app/i18n/i18n.ts`. The same list is what
   widgets may be shown in (see below), so a widget's `de.ts` only takes effect
   once the host ships German.

The locale is picked from the OS languages at startup (`initLocale()` in both
entry points). `i18n.assert.ts` checks every catalog. It fails on keys that don't
exist in English, on placeholders that differ from the English ones, and on a
plural message that turns into a plain string.

## Widgets

Every extension can carry its own translations in `extensions/<id>/i18n/`, one
file per locale:

```
extensions/stopwatch/
  manifest.json      English name, description, palette actions (unchanged)
  i18n/
    en.ts            the widget's own strings: the source catalog
    de.ts            a translation (optional)
```

The formatter, the types and the checks come from `@sdk/i18n` (MIT). The host
uses the same module, so plurals and placeholders work the same in both.

### Text the widget draws

Declare the source catalog `as const` with a default export. Then build a
translator in `setup` from `ctx.locale`:

```ts
import { createTranslator } from "@sdk/i18n";
import en from "../i18n/en";
import de from "../i18n/de";

const { t } = createTranslator(en, { de }, () => ctx.locale);
t("laps.entry", { number: 3 }); // typed exactly like the host's t()
```

Hand `t` to the view through the model, as `extensions/stopwatch/` does.

`ctx.locale` is the **host UI language**. It is one of the locales the host
ships, never more, so a widget with a German catalog stays English in an English
app instead of mixing languages on one desk. It is fixed for the life of the app.
For dates and numbers that should follow the OS region rather than the UI
language, pass `undefined` as the `Intl` locale. Sandboxed packages receive the
same value: it travels in the init message (`sandbox-guest.ts`).

### Text the host draws for the widget

The widget name and description, settings labels and palette actions are drawn
by the host. Their English stays where it is, in `manifest.json` and the widget
definition. A translation overlays them with **host keys**:

| Key | Translates |
|---|---|
| `extension.displayName`, `extension.description` | the extension in Settings |
| `widgets.<w>.displayName`, `widgets.<w>.description` | a widget in the catalog |
| `widgets.<w>.config.<field>.label` | a settings field |
| `widgets.<w>.config.<field>.options.<value>` | one option of a select |
| `widgets.<w>.actions.<id>.title` / `.subtitle` | a widget's palette action |
| `widgets.<w>.actions.<id>.params.<param>.placeholder` | a parameter chip |
| `actions.<id>.title` / `.subtitle` / `.params.<param>.placeholder` | a standalone action |

Host keys appear only in translations, never in `en.ts`.
`core/app/extension-host/localizeExtension.ts` applies them when the bundled
catalog loads.

### Checks

`scripts/extensionCatalogs.assert.ts` runs with `pnpm run verify`. It fails on:

- a file not named after a locale tag
- a missing default export
- host keys in `en.ts`
- widget keys that `en.ts` lacks, or whose placeholders or plural forms differ
- a host key that names no widget, field, option or action the extension
  declares (after a rename, this is the only signal)

## Not covered yet

- **Most host and widget strings.** So far `t()` covers only the Settings shell
  and nav, About, the bulk-add copy and the stopwatch widget. Other surfaces and
  widgets move over as they are touched.
- **Search keywords** (Settings nav, `keywords` in manifests) stay English. They
  are search vocabulary: a translation should add words, not replace the
  English ones.
- **Runtime packages** (the older `kavibay-runtime.js` tier) get no locale yet.
  Contract packages do.
- **Rust strings** (tray menu, errors returned by commands).
- **A language picker.** Only one language ships, so there is nothing to pick.
